# 0011. Répétition espacée : FSRS-6 implémenté dans le domaine

- Statut : accepté
- Date : 2026-10-29

## Contexte

La révision repose sur la répétition espacée (CLAUDE.md, section 6.2). L'algorithme retenu est **FSRS**, celui des
versions récentes d'Anki : il modélise pour chaque carte une **stabilité** (en jours), une **difficulté** (1 à 10) et
une **récupérabilité** (probabilité de se souvenir). Il reste à décider : bibliothèque ou implémentation maison,
quelle version de l'algorithme, et comment organiser les sessions et l'enregistrement des réponses.

## Options envisagées

1. **Bibliothèque Java existante** (portages communautaires de FSRS)
   - ✅ Moins de code à écrire
   - ❌ Portages peu maintenus, souvent en retard d'une version (FSRS-4.5 ou FSRS-5) ; dépendance dans le domaine,
     qui doit rester du Java pur
2. **Implémentation maison de FSRS-6**, transcrite de l'implémentation de référence py-fsrs
   - ✅ Une centaine de lignes de formules, lisibles et testées ; aucune dépendance
   - ✅ Vérifiable : les tests de py-fsrs donnent des intervalles exacts à reproduire
   - ❌ Les évolutions de l'algorithme sont à reporter à la main
3. **Algorithme plus simple** (SM-2, boîtes de Leitner)
   - ✅ Trivial à implémenter
   - ❌ Nettement moins précis ; contraire au cahier des charges

## Décision

On choisit l'option 2.

- **Algorithme** : FSRS-6 (21 poids, ceux par défaut de py-fsrs), rétention visée de 90 %, intervalle maximal de
  100 ans, étapes d'apprentissage de 1 et 10 minutes, étape de réapprentissage de 10 minutes. La rétention et le quota
  de nouvelles cartes sont réglables (`recallio.review.*`).
- **Sans fuzz** : py-fsrs ajoute par défaut un léger aléa aux intervalles pour étaler la charge. On s'en passe en V1 :
  le planificateur est déterministe, donc testable sans graine aléatoire. À reconsidérer si les révisions se
  concentrent sur certains jours.
- **Vérification** : `FsrsSchedulerTest` reproduit les scénarios de `tests/test_basic.py` de py-fsrs (intervalles
  `0, 2, 11, 46, 163, 498, 0, 0, 2, 4, 7, 12, 21` ; stabilité et difficulté après un oubli). Arrondi au pair le plus
  proche (`Math.rint`), comme le `round()` de Python.
- **État** : une ligne `review_state` par couple (utilisateur, carte) ; l'absence de ligne signifie « nouvelle ». Les
  entités JPA sont séparées du domaine.
- **Journal** : `review_log` append-only (un déclencheur interdit les `UPDATE`), avec l'état obtenu après chaque
  révision. Il servira à réentraîner les poids et aux statistiques.
- **Idempotence** : le client choisit un `requestId` par réponse. Le service verrouille l'état de la carte
  (`SELECT … FOR UPDATE`), vérifie le journal, puis insère avec `ON CONFLICT (request_id) DO NOTHING`. Une requête
  rejouée renvoie le résultat enregistré (200 au lieu de 201) ; un `requestId` réutilisé pour une autre réponse est
  refusé (409, `review.request-id-conflict`).
- **Session** : la file contient d'abord les cartes dues, de la plus en retard à la moins en retard, puis des cartes
  nouvelles dans l'ordre du programme, dans la limite du quota du jour (compté depuis minuit dans le fuseau de
  l'utilisateur). Chaque carte est accompagnée de l'échéance que donnerait chacune des quatre notes.
- **Frontières** : le module `review` obtient les cartes par `content.CardDirectory` et l'utilisateur par
  `user.CurrentUser`. Pas de clé étrangère vers les tables des autres modules.

## Conséquences

- ➕ Algorithme à l'état de l'art, sans dépendance, vérifié contre la référence.
- ➕ Une réponse envoyée deux fois (réseau mobile) n'est comptée qu'une fois.
- ➕ Le journal permettra plus tard d'optimiser les poids par utilisateur.
- ➖ La file est composée en mémoire (toutes les cartes du filtre et tous les états de l'utilisateur) : suffisant pour
  quelques milliers de cartes, à revoir (requête SQL dédiée ou état dénormalisé) si le catalogue grossit fortement.
- ➖ Sans clé étrangère, la cohérence entre modules repose sur les façades. Les cartes ne sont jamais supprimées
  (ADR 0009), donc pas d'état orphelin en pratique.
- 🔁 Le quota de nouvelles cartes est un réglage global ; il deviendra une préférence de l'utilisateur si le besoin
  apparaît.
