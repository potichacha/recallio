# 0006. Java 21 au lieu de Java 25

- Statut : remplacé par 0007
- Date : 2026-10-29

## Contexte

L'ADR 0002 retenait Java 25, la LTS la plus récente. Le poste de développement
dispose déjà de Java 21 (Temurin), qui est aussi une LTS.

Les fonctionnalités du langage dont le projet a besoin (CLAUDE.md, section 4.3)
existent toutes en Java 21 : `record`, interfaces `sealed`, pattern matching dans les
`switch` exhaustifs, record patterns et virtual threads.

## Options envisagées

1. **Java 25**
   - ✅ Variables anonymes `_`, Stream Gatherers, constructeurs flexibles, Scoped Values
   - ✅ Virtual threads sans pinning sur `synchronized` (JEP 491), en-têtes d'objet compacts
   - ✅ Support plus long, ce qui repousse la prochaine migration
   - ❌ Outillage plus récent à suivre (Error Prone, plugins Maven), JDK à installer
2. **Java 21**
   - ✅ Déjà installé ; la version la plus éprouvée par Quarkus, Error Prone, NullAway et les hébergeurs
   - ✅ Couvre tous les besoins du langage identifiés pour la V1
   - ❌ Pas d'accès aux fonctionnalités 22 à 25 ; migration à prévoir plus tôt

## Décision

On choisit **Java 21 (LTS, Temurin)** pour le backend : `maven.compiler.release=21`,
avec la même version en local, en CI et dans l'image Docker.

## Conséquences

- ➕ Aucun changement d'environnement ; outillage le plus stable possible.
- ➖ Pas de `_` pour les variables inutilisées, ni de Gatherers, ni de code avant `super(...)` :
  on s'en passe ou on écrit un équivalent classique.
- ➖ Avec des virtual threads, éviter `synchronized` autour d'opérations bloquantes
  (préférer `ReentrantLock`), à cause du pinning en Java 21.
- 🔁 À reconsidérer au plus tard à l'approche de la fin du support de Java 21, ou plus tôt
  si une fonctionnalité de Java 25 devient vraiment utile. La migration 21 → 25 est
  rétrocompatible pour le code : il suffira de changer la version du JDK et de
  `maven.compiler.release`, avec un nouvel ADR.
